# モバイルアプリ化 技術的実現性レポート

## 背景・目的

現在 bm-map-posting は Cloudflare Workers + D1 上で動く、市区町村単位でデプロイされる
Web アプリ（区画ごとの配布実績・担当者管理システム）。これを iOS/Android のモバイルアプリ化し、

1. 起動時に市区町村コードを入力
2. 地図データをダウンロード
3. データを端末ローカルに保存

というフローを実現したい、という要望に対する技術的実現性の検討。開発環境は Chrome OS / Windows 11
（**Mac なし**）という制約がある。

### 確認済みの現状（コードベース調査結果）

- **フロントエンド**: フレームワークなしの素の JS/HTML/CSS。ビルドステップなし。地図は Leaflet 1.9.4
  を CDN `<script>` タグ（SRI ハッシュ付き）で読込み。`public/index.html` + `public/app.js`（約54KB、
  1ファイル）が地図画面の実体。PWA関連の仕組み（manifest.json、service worker）は一切なし。
- **背景地図タイル**: `public/app.js` で OpenStreetMap の生タイル
  (`{s}.tile.openstreetmap.org/{z}/{x}/{y}.png`) をオンラインで都度取得している。
- **バックエンド**: Cloudflare Workers（Static Assets 機能、`run_worker_first: true`）。
  `worker/index.ts` が `/api/*` と `/config.js` を処理し、それ以外は `public/` の静的ファイルに
  フォールスルー。**市区町村ごとに別々の Worker デプロイ + 別々の D1 データベース**
  （`wrangler.jsonc` の `env.<地域ID>`。例: `14213-yamato`, `14206-odawara`, `14203-hiratsuka`,
  `14117-aoba`）。複数地域を1つのバックエンドが動的に振り分ける仕組みは現状存在しない。
- **地図データ量**: 地域ごとに `boundary.geojson`（区画/青線、約2.1〜2.8MB）+
  `boundary_chome.geojson`（エリア/紺線、約350〜700KB）。合計おおむね2.4〜3.5MB（非圧縮）。
  gzip/brotli圧縮でさらに縮小見込み。モバイル端末へのダウンロードは十分現実的なサイズ。
- **可変データの同期**: 担当者・配布実績（`term_data`）は GeoJSON ではなく D1 にあり、
  `worker/records.ts` の `/api/record`（配布数の差分加算）、`/api/assignee`、`/api/area-manager`
  で読み書きする。**単純なダウンロードだけでなく双方向同期が必要**。`recordDistribution` は
  差分加算方式（`newTotal = 既存値 + delta`）のため順序に依存しない同期に向いているが、
  **冪等性キー（同じ操作の重複適用を防ぐ仕組み）が現状スキーマに存在しない**ため、オフライン時に
  記録した操作をリトライ付きで送信する設計にはそのままでは使えない。
- **認証**: `worker/auth.ts` によるステートレスな HMAC 署名トークン方式（12時間TTL、リフレッシュ
  機構なし）。モバイルクライアントへの移植は容易（トークンを保存し `Authorization: Bearer` で送るだけ）。

### 前提条件（検討時に確認済み）

- 背景地図タイル（道路・建物などの画像）はオフライン完全対応**不要**。オンライン時のみ表示で良い。
  オフラインで必須なのは**区画ポリゴンデータ**（配布実績・担当者情報を含む）のみ。
- 技術スタックは既存のバニラ JS / Leaflet 資産をそのまま活かす方向（Capacitor）で検討する。

この前提により、OSMタイル利用規約に抵触する自前タイル配信パイプラインの構築は**不要**となり、
スコープが大きく簡素化される。

---

## 結論：技術的実現性

**十分に実現可能。** 最大のリスクは「Macなし」という制約だが、これはクラウドビルドサービス
（後述）で完全に解消できる既知のパターンであり、新規に発明が必要な要素はない。次に大きい作業は
バックエンド側のオフライン同期対応（冪等性キー・差分取得エンドポイントの追加）だが、これも
既存スキーマ（`term_data.last_updated_at` 等）を活かせば小〜中規模の追加実装で済む。

## 推奨アーキテクチャ

### 1. 技術スタック: Capacitor（既存Webアプリのラップ）

| 観点 | 内容 |
|---|---|
| コード再利用 | `public/app.js`・Leaflet描画ロジック・全 `fetch()` 呼び出しがほぼそのまま WebView内で動作。書き直しはほぼ不要。 |
| Macなしでの iOS ビルド | Capacitor は Xcode プロジェクト（ネイティブシェル）を生成するだけで、**ビルド自体は GitHub Actions の `macos-latest` ランナーや Codemagic 等のクラウドCIに委譲可能**。署名済み `.ipa` を作成し TestFlight に配信でき、開発者は物理Macを一度も使わずに済む。Apple Developer Program（年間$99）への登録は方式によらず必須。実機テストはローカルSimulatorが使えない分TestFlight経由のみになる（イテレーション速度はやや落ちるが実用上問題ない）。 |
| Android | Windows/Chrome OS 上の Android Studio でローカルビルド・実機テストとも問題なく可能。 |
| 他の選択肢との比較 | React Native/Expo・Flutter は Macなしビルドの成熟度は同等以上だが、UIレイヤー（`index.html`/`app.js` のメニュー・モーダル・地図操作ロジック）の全面書き直しが必要になり、既存資産をほぼ活かせない。今回は既存資産活用の方針により Capacitor を採用。 |

### 2. 市区町村コード → バックエンドURLの解決

現状は地域ごとに別Workerデプロイ（別URL・別DB）のため、アプリが入力されたコードから
接続先を引けるようにする「地域ディレクトリ」が必要。

- `{コード: {regionId, 表示名, apiBaseUrl, hasChomeBoundary, 地図中心/ズーム}}` という小さな
  JSON を用意し、アプリに同梱（オフライン起動時のフォールバック）しつつ、起動時にオンラインなら
  最新版を取得してローカルにキャッシュする。
- このJSONの生成・更新は、既存の地域追加スクリプト `scripts/new-region.mjs`（`wrangler.jsonc` へ
  の `env.<地域ID>` 追加を自動化している）に一手順追加する形が自然。新規地域追加のたびに
  ディレクトリも自動更新される。
- ディレクトリ自体の配信元は、専用の小さな静的ホスティング（Cloudflare Pages や KVバックエンドの
  軽量Worker）で十分。

### 3. オフラインデータ設計

- **オフライン必須**: `boundary.geojson` / `boundary_chome.geojson`（区画・エリア境界）と
  `areas` / `term_data`（担当者・配布実績）。端末ローカルに SQLite（`@capacitor-community/sqlite`
  等）またはファイル保存（`@capacitor/filesystem`）で保持。
- **オンライン時のみでよい**: 背景地図タイル（既存の `L.tileLayer(OSM)` をそのまま利用、変更不要）。
  電波のない場所では区画ポリゴンだけが表示され、背景の道路・建物画像は表示されない、という
  仕様になる。
- この前提により、当初検討していた「地域ごとの自前タイルパッケージ配信」（Planetiler等での
  タイル生成・R2配信）は**不要**。スコープから除外してよい。

### 4. バックエンド側で新規に必要な作業

1. **差分取得エンドポイント**（新規）: `GET /api/sync/changes?since=<timestamp>` のような形で、
   `term_data.last_updated_at`（既存カラム）を使い、前回同期以降の変更のみを返す。毎回全件
   ダウンロードする必要がなくなる。
2. **冪等な一括書き込みエンドポイント**（新規）: オフライン中に記録した配布実績・担当者変更を
   まとめて送信する `POST /api/sync/batch`。クライアント生成の一意な操作ID（`client_op_id`）を
   `activity_log` に追加保存し、同じ操作が再送されても二重加算しないようにする
   （**現状スキーマにこの冪等性の仕組みがないため、`migrations/` に新しいマイグレーションが必要**）。
3. **トークン失効の扱い**: 12時間TTLのトークンはオフライン期間がそれを超える可能性がある
   （例: 週末の配布作業）。最小対応は「同期時にトークン切れなら再ログインを促す」UXのみで
   バックエンド変更不要。より堅牢にするならリフレッシュトークン機構を `worker/auth.ts` に追加。

いずれも `worker/records.ts` の既存ガード（世帯数超過防止・マイナス防止）や差分加算方式
（順序に依存しない）という設計をそのまま活かせるため、大掛かりな作り直しにはならない。

## 段階的な進め方（推奨フェーズ）

1. **フェーズ0（数日、リスク検証）**: 既存アプリをそのまま・オンライン専用でCapacitorに包み、
   クラウドCIでビルドした署名付き `.ipa` をTestFlightで実機インストール、Androidも実機で
   動作確認。「Macなしで本当にiOS配布まで到達できるか」を最初に検証する。
2. **フェーズ1（小規模）**: 市区町村コード入力画面＋地域ディレクトリ解決の実装。これは
   モバイルリポジトリ側で持つ独自コピーのフロントエンドに対して行う（`public/app.js` 本体は
   改修しない。詳細は後述「マージ後もWeb版は維持されるか」を参照）。
3. **フェーズ2（中規模）**: 境界GeoJSON・区画/実績データのローカル保存とオフライン読み込み対応。
   バックエンド側に差分取得エンドポイントを追加。
4. **フェーズ3（最大規模、バックエンド中心）**: オフライン時の書き込み（配布記録・担当者変更）を
   ローカルキューに貯め、冪等な一括送信で同期。`migrations/` に冪等性キー用のカラム/テーブル追加。

この順序により、最もリスクが高い「Macなし前提」を最初に潰し、最もバグを生みやすい
「オフライン書き込み同期」を最後の専用フェーズに回す。

## バージョン管理方針：ブランチ分割 vs リポジトリ分割

「現行の bm-map-posting は維持したい（壊したくない）」という前提のもと、モバイル関連の開発を
どこに置くべきかを検討する。今回のモバイル化作業は性質の異なる2種類の変更を含む。

- **(A) バックエンド側の追加**（フェーズ2〜3で必要になる `/api/sync/changes`・
  `/api/sync/batch`・冪等性キー用マイグレーション等）: これは `worker/`・`migrations/` という
  **既存の共有コード**への追加であり、Web版・モバイル版を問わず全地域デプロイで使われる
  唯一のバックエンド実体。別リポジトリに複製する意味がない。
- **(B) モバイルクライアント本体**（Capacitorプロジェクト、`ios/`・`android/` ネイティブ
  シェル、モバイル専用CI/署名設定など）: 既存の `public/` を土台にするが、成果物としては
  現行Webアプリと全く別の配布形態（アプリストア）を持つ。

この2つは分けて方針を考えるのが妥当。

### (A) バックエンド追加分：現行リポジトリ内のブランチで開発（推奨）

新しいエンドポイント・カラムの追加のみで既存機能を変更しない設計にすれば、通常の
feature ブランチ（例: `mobile-sync-api`）→レビュー→`main` マージ→各地域へ
`wrangler deploy --env <地域ID>` という既存フローにそのまま乗せられる。別リポジトリに
分離すると `worker/records.ts` のガード条件（世帯数超過防止等）やスキーマ定義の
二重管理が発生し、「現行を維持したい」という意図に反してかえって事故リスクが上がる。

### (B) モバイルクライアント：別リポジトリを推奨

以下の理由から、Capacitorプロジェクト本体は新規リポジトリ（例: `bm-map-posting-mobile`）
として切り出すことを推奨する。

1. **依存関係の性質が大きく異なる**: 現行 `package.json` は `devDependencies` のみ
   （wrangler・typescript）でランタイム依存ゼロ、ビルドステップなしという構成を意図的に
   保っている。Capacitor導入は `@capacitor/core`・`@capacitor/ios`・`@capacitor/android`・
   各種プラグイン、`ios/`（Xcodeプロジェクト）・`android/`（Gradleプロジェクト）一式、
   大量の `node_modules` を持ち込み、この単純さを崩す。
2. **リリースサイクルが根本的に別物**: Workers側は `wrangler deploy` で即時反映できるが、
   モバイル側はApp Store/Google Playの審査を伴い、バージョン番号・リリースノート・
   ストア掲載情報などアプリ配布特有の管理が必要になる。同じリポジトリのIssue/PR運用に
   混在させると、両者のリズムの違いがそのまま管理コストになる。
3. **シークレットの分離**: Apple配布証明書・プロビジョニングプロファイル・Google Play
   署名鍵といったモバイル専用シークレットは、Cloudflare/Wranglerのトークンとは完全に
   独立して管理すべきもの。CI設定を同一リポジトリにまとめると誤操作・誤公開のリスクが増す。
4. **技術的な結合は薄い**: モバイルアプリはバックエンドAPI（新設する `/api/sync/*` を含む）
   をHTTP経由で呼ぶだけの「外部クライアント」であり、`worker/` 側のソースコードを直接
   参照・共有する必要がない。リポジトリを分けても実装上の支障はない。

両リポジトリ間の連携は強いモノレポ的結合ではなく、モバイルリポ側に「対応する
バックエンドAPIバージョン／必須エンドポイント一覧」を明記する程度の緩い連携で十分。

### まとめ

| 変更内容 | 置き場所 |
|---|---|
| `/api/sync/*` 等バックエンド追加、マイグレーション | 現行リポジトリ内のfeatureブランチ→レビュー→main |
| Capacitorモバイルアプリ本体（ios/・android/・CI・署名設定） | 新規リポジトリ（例: `bm-map-posting-mobile`） |

### マージ後もWeb版は維持されるか

**バックエンド（`worker/`・`migrations/`）側の変更に限れば、Web版の機能を壊さずに両立できる。**
理由は次の2点で、いずれも「既存の挙動を変更せず追加するだけ」に設計を限定できるため。

- 新規エンドポイント（`GET /api/sync/changes`・`POST /api/sync/batch`）は既存の
  `/api/areas`・`/api/record` 等の**ルートに一切触れない**、純粋な追加。
- 冪等性キー用のカラム（`client_op_id` 等）は既存テーブルへの **nullable な列追加**
  にとどめれば、既存のクエリ・書き込みロジックへの影響はない。

したがってこの範囲であれば、ブランチを `main` にマージ→各地域へ再デプロイしても、
**Web版ユーザーの体験は文字通り何も変わらない**（新しいAPIが増えるだけで、既存ルートも
`public/` の配信内容も無変更）。

**一方、`public/app.js` を直接改修する形（fetchの接続先を可変にする、市区町村コード入力画面を
追加する等）は、Web版を壊すリスクがある。** `public/app.js` は各地域のWorkerが**Web版ブラウザ
利用者に実際に配信している本体そのもの**であり、モバイル対応のための分岐処理を同じファイルに
混在させると、`CLAUDE.md` に記録されている過去の事故例（`#header` へのCSS変更が
`#menu-panel` を巻き込んで消えた一件）と同種の「意図しない副作用でWeb版が壊れる」
リスクを新たに持ち込むことになる。

**方針**: モバイル向けのUI・接続先切り替え・オフライン保存ロジックは、
**`public/app.js` を直接改修せず、モバイルリポジトリ側に独立したコピーとして持つ**。

- モバイルアプリ（Capacitor）は `public/app.js` をそのまま参照・同梱するのではなく、
  モバイル向けに調整した独自版をモバイルリポジトリ内に置く（地図描画などLeafletの
  扱い方自体は流用できるが、ファイルとしては別管理）。
- こうすることで、バックエンド側のブランチマージは「純粋な追加のみ」に保たれ、
  Web版の配信物（`public/`）は一切変更されない → **Web版とモバイル版は完全に独立して
  共存できる**。
- トレードオフとして、地図描画ロジック等に手を入れる場合はWeb版・モバイル版の両方に
  同じ修正を反映する手間（コードの二重管理）が発生する。これは意図的な安全側の選択
  （「現行を維持したい」という要件を優先した結果）である。将来的に共通化したくなった
  場合は、両者が呼び出す純粋な描画・データ変換関数だけを小さな共有モジュールとして
  切り出す、という段階的な対応が考えられる。

## 検証方法（この分析の妥当性を確かめる手段）

- フェーズ0の妥当性は、実際に最小のCapacitorプロジェクトを作り、GitHub Actions等の
  `macos-latest` ランナーでの `.ipa` ビルド〜TestFlight配信を一度通しで試すことで直接検証できる
  （コストはCIの実行時間とApple Developer Program登録のみ）。
- 冪等性キー設計の妥当性は、`worker/records.ts` の `recordDistribution` に対して同一
  `client_op_id` を持つリクエストを意図的に二重送信し、`distributed_total` が一度しか
  加算されないことをテストすれば確認できる。
- 差分取得エンドポイントの妥当性は、`term_data.last_updated_at` を更新後に
  `since=<更新前の時刻>` で問い合わせ、更新された行のみが返ることを確認すればよい。

これらはいずれも次フェーズ（実装フェーズ）着手時に検証すべき項目であり、本レポートでは
設計上の妥当性確認にとどめる。
